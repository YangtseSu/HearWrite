## 3. 🔴 阻断级

### 3.1 `MIGRATION_4_5` 依赖的 `DROP COLUMN` 在 API 33 上不存在

`app/src/main/java/org/yangtse/hearwrite/data/HearWriteDatabase.kt:326-332`

```kotlin
/**
 * `DROP COLUMN` needs SQLite ≥ 3.35 (API 33+, which is this app's floor), so no
 * table rebuild is required: …
 */
val MIGRATION_4_5 = object : Migration(4, 5) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE `history` DROP COLUMN `enrichedText`")
    }
}
```

该 KDoc 的"3.35 = API 33+"是错的：

- `ALTER TABLE … DROP COLUMN` 由 **SQLite 3.35.0**（2021-03-12）引入（sqlite.org 发布日志）。
- Android 官方 SQLite 版本表（AOSP `core/java/android/database/sqlite/package.html`）：**API 33 → 3.32**、API 32/31 → 3.32、API 34 → 3.39。
- `app/build.gradle.kts:49` = `minSdk = 33`。
- 工程未引入自带 SQLite：`grep -rn sqlite app/build.gradle.kts gradle/libs.versions.toml` 无命中，即走框架 SQLite（`androidx.sqlite:sqlite-framework`），语句由设备的 3.32 引擎解析。

**影响**：任何 v4 老库（0.8.0 安装）升到 0.9.0，在 Android 13（API 33）上首次打开数据库即 `SQLiteException: near "DROP": syntax error`；`HearWriteDatabase.create` 只注册 4 个迁移且**没有** `fallbackToDestructiveMigration`，数据库永远打不开 → 错词本 / 收藏 / 历史 / 听写统计全部失效。且 `ui/HomeViewModel.kt:368-396` 的两个收集器（`historyRepository.observe()`、`wrongWordsRepository.observeMarks()`）没有 `catch`，异常逃出 `viewModelScope.launch` → **进程崩溃**。这恰与本版卖点"升级不丢数据"相反。新装用户不受影响（直接建 v5 表）。

**现有门禁看不见它**：`HistoryEnrichedDropMigrationTest` 跑在 CI 的 API 36 模拟器（`.github/workflows/build.yml:122` `api-level: "36"`，SQLite 3.50）；walkthrough 记录也是 API 37。

**同一错误等式复现于文档**：`docs/implemented/2026-09-18-DATA-MODEL.md` §6 Phase 3（当时行号 `:290` 写作 "SQLite ≥ 3.35 / API 33+"、`:301` 写作 "SQLite ≥ 3.35 = API 33+，不必重建表"；该处现已改为表重建）。

**修法（二选一）**

1. 可移植的表重建（Room 为旧 SQLite 生成的就是这一形状）：
   `CREATE TABLE history_new(id TEXT NOT NULL PRIMARY KEY, text TEXT NOT NULL, createdAt INTEGER NOT NULL); INSERT INTO history_new SELECT id, text, createdAt FROM history; DROP TABLE history; ALTER TABLE history_new RENAME TO history;`（同时保持 `MIGRATION_4_5` 的"授权原文不动"语义）。
2. 按 AGENTS.md 的 `minSdk` 政策抬高下限到 34（代价是排除 Android 13 设备）。

无论哪种，都应同步修正上述两处文档，并让迁移测试套件能在 API 33（或更低 SQLite）上跑一次——否则这一类问题永远测不到。

## 4. 🟠 主要缺陷

### 4.1 生成器把单套音标复制成"英美两套"（11,438 条）

`scripts/build-lexicon.py:426`

```python
entry["i"] = [us or uk, uk or us]
```

只有一侧有来源时，另一侧被原样复制。用已缓存源（`.cache/ipa-en_US.txt` / `.cache/ipa-en_UK.txt`）与资产逐条比对：

```
ipa-dict 只有美式 → 5,577 条，资产 i[0] == i[1] 全部为 True
ipa-dict 只有英式 → 5,861 条，资产 i[0] == i[1] 全部为 True
合计 11,438 条
```

例：`abase → ["ɐbˈeɪs","ɐbˈeɪs"]`（真英式被同时标成"美"）、`aargh → ["ˈɑɹɡ","ˈɑɹɡ"]`（真美式被标成"英"）。

这直接违反 `docs/implemented/2026-09-18-DATA-MODEL.md` §4.2 的显示规则"**只查到一套时显示一套、不标另一套**"：`domain/WordDisplay.kt` 的 `ipaLabels` 只要两侧非空就并列打印 `英 … · 美 …`，运行时无从分辨"两套"与"一套复制"。约 592 个已上架词表行因此显示伪造的第二种音标。

`ResolvedWord.kt` 里 `Ipa`/`IpaSerializer` 的 KDoc 自称"允许空槽（a source may print only one）"，但生成器从不下空槽（`IpaSerializer`: "the asset never writes a hole"）——空值能力与 §4.2 的规则**同时**是死代码。

**修法**：生成器对缺失侧写 `null`，让 `ipaLabels` 只打印存在的一套；或在规范里明确承认"单源复制"并删掉 `Ipa` 的空值叙事。二者取一。

### 4.2 仁爱音标提取器丢弃 `/a; b/` 形态的教材读音（65 词头 / 约 385 行）

`scripts/extract-renai-ipa.py` 的 `parse_line`：先用 `GROUP_RE = /([^/]{1,40})/` 取整组，再做 `set(reading) - IPA_CHARS` 校验；`;` 不在 `IPA_CHARS` 里，于是**整组被 `continue` 丢掉**。正确顺序应是先按 `;` 切分、再逐条校验。

用本机 OCR 源重放并打"先切分"补丁对比：

```
lines where `;`-splitting recovers entries: 64
distinct headwords recovered: 65        # clothes / a / the / as / can / with / either …
shipped rows carrying them: 385         # 已上架词表中受影响的原始行数
shipped IPA != textbook IPA: 63         # 例：clothes 教材 /kləʊdz; kləʊz/，资产 /ˈkɫoʊðz/ · /klˈəʊðz/
```

丢掉的恰好是英美差异最大的功能词，且与 AGENTS.md / §3.2 的"教材优先"契约冲突。提取器自述的"按音标组拒绝，一条损坏只丢自己那一条"在含 `;` 时并不成立。

**修法**：先切分再校验，重跑 `extract-renai-ipa.py` → `build-lexicon.py`，并把 `;` 形态加进提取器的单测。

### 4.3 拨盘提示行被静默截断，且没有"展开全部"出口

- `domain/DialFit.kt:332`：`fun dialFit(word: String?, gloss: String?, hasHint: Boolean, metrics: DialMetrics)` —— **只收"有没有提示"，从不测量提示文本**。
- `ui/DictationScreen.kt:1274-1282`：提示 `Text` 为 `maxLines = 1` + `TextOverflow.Ellipsis`。

于是当 `/音标/ 词性` 比内容框宽、而词与释义都放得下时，`needsDetail == false`（不出现"展开全部"），被吃掉的永远是词性。这违反 `DialFit.kt:330` 自己写下的不变量——

> Nothing that truncates is ever shown without `DialFit.needsDetail` being true.

——也与 `docs/implemented/2026-09-18-DATA-MODEL.md` §4.1 的"0 溢出"结论冲突：那次数的是**只有音标**的宽度（最大值 10.0 u 已贴住 9.84 u 的框）。

按仓库自己的 `displayWidth`（全角 1 / 半角 0.5）独立量测：**125 个已上架英文行**拼出的提示超过 9.83 u（147.5 dp 那个内容框）。

| 位置 | 行的词性列 | 合成提示 | 宽度 |
|---|---|---|---|
| `仁爱版初中/七上 Unit 4 探究.txt:13` | `prep. & conj.` | `/bɪˈfɔː(r)/ prep. & conj.` | **12.5 u ≈ 187 dp** |
| `中考1600/C.txt:104` | `n.` | `/kənˌɡrætʃəˈleɪʃn/ n.` | 10.5 u |
| `人教版初中/九全 Unit 1.txt:2` | `n.` | `/ˌkɑːnˈvərˈseɪʃn/ n.` | 10.0 u |

改前拨盘只渲染 `row.pos`，没有任何已上架行超宽——这是**新增的合成提示行引入的**回归类别。

**修法**：把提示文本（或其 `displayWidth`）喂给 `dialFit`，超宽即置 `needsDetail`；或在提示过宽时把该行让给详情卡。

## 5. 🟡 次要缺陷

### 5.1 C6 的 BESIDE 宽度预算与渲染不一致

`domain/DialStage.kt:134-136` 的宽度判据用 `readoutsWidthDp`，调用处传 `STAGE_READOUTS_WIDTH = 220.dp`（`ui/DictationScreen.kt:159`、`:908`，其 KDoc 自称"两侧动作键最小值 + 展开全部 / 秒数块"）。而实际渲染的 beside 行是：

```
dial + Spacer(DIAL_STAGE_BESIDE_GAP = 16.dp)
     + Row(展开全部, 秒数, wordActions(Modifier.width(STAGE_ACTIONS_MAX_WIDTH = 420.dp)), spacedBy(12.dp))
```

（`:1068`、`:1084-1091`。）预算漏掉了 beside 间隙、行内两个 12 dp，以及被固定到 **420 dp 上限**的动作块。触发面：宽 ≥ 600 dp（`twoColumnsAllowed`）且舞台高 ∈ [248, 398) dp 的窗口（分屏 / 自由窗口），会选中 BESIDE 而行放不下，两个 `weight(1f)` 按钮被压进固定 `height(52.dp)`（`取消标记` 换行后裁切）。真机 walkthrough 没命中只是因为横屏 923 dp 恰好够。既然 C6 主张"'表盘放得下' 是算术的性质"，应把真实行宽喂进求解器。

### 5.2 `WordKind` 由 `display` 而非 `speak` 判定

`domain/WordKind.kt:27-31` + `domain/Row.kt:82`：`kindOf(display)`，而 `display` 含 `= B` 展开尾巴。对合法行 `apple = 苹果`，新实现判 `WORD`（v0.8.0 用可朗读侧判 `EN`），连带四项漂移：TTS 语言（`DictationEngine.kt:390`）、朗读释义支路（`:301`，`cjkWordSpeech` 因 `speak.length != 1` 返回空 → 该遍被静默跳过）、ECDICT 查表（`WordKind.WORD` 不查）、OCR/批改语言。已上架 651 表影响为 0（3 行含 `=`，两侧都非中文），属**潜在**缺陷；AGENTS.md 那句"derived … from the display headword"与实现同错，建议一并改为 `kindOf(speak)`。

### 5.3 `check-assets.py` 比运行时解码器宽

`lexicon_entries` 之后的校验用 `if senses is not None` / `if ipa is not None`：因此 `"s": null` 与非字符串 `g` 会被判为合法，而 `LexEntry.senses: List<Sense>`（非空类型，`Json { ignoreUnknownKeys = true }`）解码时抛 `SerializationException`——CI 会放行一个运行时必炸的资产。（`"i": null` 其实安全：`ipa: Ipa?` 可空，这一条常被说重。）

### 5.4 `LibraryListsViewModel` 两处

- `ui/LibraryViewModel.kt:117`：`catch (e: Exception) { return }` 吞掉 `CancellationException`；同一提交在 20 行下（`:130-135`）对同一模式显式重抛，仓库另有 26 处重抛。当前影响为 nil（`return` 是函数最后动作），但破坏了结构化并发的一致性。
- `ui/LibraryViewModel.kt:100-103`：KDoc 称该 flag"只阻止 230 表分类问 230 次"，但 `compareAndSet` 位于 `!isCjkRun(rows)` 之后，纯中文的 230 表分类（人教版小学语文）**永远不置位**，即注释描述的正是它没防住的那一种。

### 5.5 裁剪状态机被复制两份

`HomeViewModel.startOcrCrop / cancelOcrCrop / confirmOcrCrop` 与 `DictationViewModel.startCrop / cancelCrop / confirmCrop` 是同一套"session 计数 + 解码 + recycle + gate"约 150 行的两份拷贝（共享件只有 `OcrCropOverlay` 组合式）。当前两份一致，但与 AGENTS.md "不要手写第二版共享件"的原则相悖，下一次改动极易只改一侧。
